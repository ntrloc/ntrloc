Security model

Default deny. Always audited.

Permissions aren't a layer bolted onto ntrloc's data model — they're evaluated as part of the same commit pipeline that writes the data itself.

Permission model

Markers, grants, and rules

Three primitives compose into everything ntrloc's access control needs to express.

Policy markers

Simple identifier tags applied to items and links. A marker carries no logic of its own — it's the attachment point for permission grants.

Permission grants

A user or group is granted specific operation primitives on a marker — item create/read/delete, property read/write, link create/read/delete, binary download, and more. Effective permissions are the union across every marker applied to an item.

Marker assignment rules

Declarative rules that automatically apply or remove markers based on an item's own properties, or properties of related items reached via a declared, bounded traversal path — never open-ended graph exploration. Rules fire as part of the commit pipeline, so a marker change is never asynchronously lagged behind the property change that triggered it.

Temporary overrides

A privileged user can grant specific permissions to specific users on a specific item, time-bounded by a mandatory expiry and a mandatory reason. Nothing about ntrloc's override model allows a permanent, unaudited exception.

Five rules the model never breaks

  • Default deny — no permission exists unless explicitly granted.
  • Union across markers — every marker on an item contributes its grants.
  • Write implies read — there is no such thing as a write-only property.
  • All-or-nothing proposals — one disallowed property in a mutation rejects the whole proposal.
  • Superusers bypass policy, never audit — every action is still fully logged.

A schema that only shows you what you can touch

The schema endpoint returns a caller-scoped projection: item types you can't see are omitted entirely, properties appear only if you have read or write access to them (and the response says which), and link types appear only when both participant types are visible to you. There's no trial and error — the schema you're handed is a complete, accurate contract for what you're actually permitted to do.

The same discipline applies to creation. A create request passes two gates before anything is persisted: does the principal have create permission on the item type at all, and — given the properties and links the new item would actually have — would the markers it's assigned grant that principal create permission on this specific instance? If the creator wouldn't be able to see the item they're about to create, the create is rejected outright rather than silently producing an item its own author can't read back.

Explain, simulate, and preview — before anything changes

Three administrative tools turn "what does this permission change actually do" from a guess into an answer:

  • Current-state explanation — for any item, who can do what, and exactly which markers grant it.
  • Rule simulation — preview what markers would be assigned if an item's properties changed, without changing anything.
  • Change impact analysis — for a proposed security model change, how many items are affected and which users gain or lose access, with warnings for the implications you'd want flagged (like a contractor gaining access to restricted items).

Audit

Security posture has a history, not just a current state

Policy changes — rule-assigned or ad-hoc — are first-class events in the write layer, versioned the same way property changes are.

Ad-hoc markers

Applied manually by privileged users, persistent against rule precedence, but never permanent — a TTL is mandatory, and both creation and expiry are audited.

Full item history

An item's history includes not just when its properties changed, but when its security posture changed, and — via the reason field — why.

Nothing lingers unaudited

Expired overrides cease to exist rather than sitting inactive; every creation, modification, and expiry is a write-layer event.
