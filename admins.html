For admins

Ship changes without a maintenance window

Every change you make — to schema, security policy, or bulk data — stages as a live, reviewable overlay before it ever goes live.

The changeset lifecycle

Define, review, then flip one switch

Define, then build

You define the schema changes, security changes, and data transformations that make up a changeset. ntrloc calculates scope and impact up front and presents a pre-commit report before anything is built, then stages an overlay in parallel — every declared transformation runs as a continuous process against the live write stream, not a one-time batch job.

Stage, then commit or discard

The staged overlay is queryable like any other view, so you and your testers can diff before/after per item and review marker changes for as long as you need. A single atomic switch makes it live — because the overlay was already current, the commit is a true switch flip, not a re-migration. Discarding costs nothing; live data is never touched until commit.

Permission tooling

Explain, simulate, and preview — before anything changes

Three tools turn "what does this permission change actually do" from a guess into an answer.

Current-state explanation

For any item, who can do what, and exactly which markers grant it.

Rule simulation

Preview what markers would be assigned if an item's properties changed, without changing anything.

Change impact analysis

For a proposed security model change, how many items are affected and which users gain or lose access — flagged when the implications matter, like a contractor gaining access to restricted items.

Schema evolution

Most schema changes aren't events

Traits are reusable and non-destructive, so most of what teams think of as "schema migrations" — adding a property, renaming a label, giving a type a new trait — are just metadata edits. There's no data to rewrite and no version to bump; only explicit data migrations advance the schema version.
