# ntrloc Index Reconciliation Summary
## Topic: Usage-Driven Index Strategy for Per-Type Property Tables

Status: **Deferred.** Raised during the item-type-inheritance design discussion (2026-08-06) because inheritance and trait cross-type queries make the same underlying question sharper, but this is not a prerequisite for inheritance itself and is being picked up as a follow-on. Nothing here is implemented.

---

## The problem

Every item type gets its own physical table (`RegisterPartitionManager.createItemTypeTable`), currently with exactly two indexes: a blanket `GIN(properties)` and `GIN(states)`, created once at table-creation time and never revisited. This is schema-agnostic and always correct — a GIN index on a whole JSONB column covers any key without needing to know property names in advance — but it's weak for range comparisons and can't serve `ORDER BY` efficiently. That matters more once cross-type queries (across traits and/or supertype descendants) need sorted, paginated results merged from several tables — that merge only stays cheap if every branch can produce pre-sorted output via a real per-property index.

Real-world type shapes make the naive answers to "so index every property" or "index none of them" both wrong:
- **Index nothing** — sort/range/selective-filter performance stays bad indefinitely. Rejected.
- **Index everything** — a deep subtype with a large combined attribute set could easily accumulate over a thousand properties once traits and a supertype chain are both folded in (corroborated in practice: a single item type with 1600+ properties has been observed in a real deployment once traits and supertypes were combined). Blanket per-property expression indexes at that width means real write amplification (every index is maintained on every `INSERT`/`UPDATE`), storage bloat, and query-planner overhead from hundreds or thousands of largely-unused indexes on one table. Rejected. At that scale it also kills the *other* unproposed-but-obvious alternative, an admin-declared `queryable` flag per property: no admin can sanely reason about 1600 individual flags and correctly predict which handful actually matter for real queries.

## Index fundamentals (recap, grounding the decision below)

- An index trades write cost + storage for read speed on a specific access pattern. Btree serves equality/range/sort; GIN serves containment/existence/multi-valued predicates.
- The query planner only uses an index when it's estimated cheaper than the alternative — driven by **selectivity** (fraction of rows a predicate matches, from `ANALYZE` statistics), whether the predicate **shape matches** the index (leading-column/expression match), whether it can **avoid a sort**, and whether stats are fresh.
- **An index that exists but that no real query plan ever picks is pure cost, zero benefit.** This is the crux of the whole discussion.
- Anti-patterns: indexing low-selectivity values (not necessarily low-cardinality — see below), indexing columns never used in `WHERE`/`ORDER BY`/`JOIN`, over-indexing write-heavy tables, redundant/overlapping indexes, indexing the wrong expression shape for the actual query pattern (e.g. plain btree when real usage is substring search, which needs trigram/full-text instead).

**Key nuance surfaced by a concrete example** (an enum-like controlled-list property vs. an unconstrained free-text property): cardinality is not the same as selectivity. A controlled-list property with reasonably distributed values can be *more* index-friendly than naive "don't index enums" intuition suggests (each value may still be quite selective). An unconstrained string's high cardinality only helps if it's actually queried by equality/prefix — if realistic usage is substring/contains search, a plain btree does nothing and a different index type (trigram GIN) would be needed instead. **Neither property's index-worthiness can be predicted from its type alone — it depends on real, observed query usage.**

### Measuring selectivity directly

Postgres has real tooling for this, with one wrinkle specific to how ntrloc stores properties (one JSONB blob per row, not one column per property):

- `ANALYZE` populates `pg_stats` per column (`null_frac`, `n_distinct`, `most_common_vals`/`most_common_freqs`, `histogram_bounds`) — but only for a real column or an *expression* Postgres already knows to track. A bare `properties` JSONB blob gives nothing property-specific on its own.
- `CREATE STATISTICS ... ON (properties->>'<propertyId>') FROM table` (extended statistics, expressions supported since PG14) gets real distribution stats for one specific property's expression *without* committing to a full index first — cheap to create, cheap to drop, the natural first step before deciding whether the real index is worth it.
- **HypoPG** (`CREATE EXTENSION hypopg`) lets you create a *hypothetical* index — zero storage, zero write cost — and then run plain `EXPLAIN` to see whether the planner would actually choose it. This is the closest thing to "just ask Postgres." Its answer is only as good as the statistics behind it, though, so it's most meaningful paired with `CREATE STATISTICS` on the same expression first. It also can't be used with `ANALYZE` (no real index exists to actually scan), so it answers "would the planner pick this" but not "how fast would it be."
- Postgres doesn't explain *why* it rejected a plan — there's no "tell me why not" output. The practical substitute is a forced A/B: `SET enable_seqscan = off` (or `pg_hint_plan` for a scoped, per-query version) and compare the forced plan's cost against the original. Common real reasons an expression index goes unused: poor/stale selectivity estimate, an expression-shape mismatch between the index and the actual query (e.g. `->>'x'` vs `->'x'`), a table too small for the index to matter, or conservative `random_page_cost`/`effective_cache_size` settings.
- Postgres also tells you, after the fact and for free, what it actually used: `EXPLAIN (ANALYZE)` names the exact index per query; `pg_stat_user_indexes.idx_scan` is a continuously-maintained per-index counter requiring no extension and no per-query ask — this is the ground-truth signal the reconciler design below leans on for its removal decision.

## The decision: usage-driven, not admin-declared

Rather than a static `queryable` flag an admin sets at schema-definition time (which forces a prediction neither the admin nor the system can reliably make — demonstrated directly by the enum/string example), index existence should be **derived from observed real usage**.

This is more tractable for ntrloc specifically than for a generic database: search never accepts raw SQL, it goes through `CollectionProjectionSpec` (item type + sort + filter + facets) — a structured object the application constructs. That means ntrloc already knows, with certainty and no log-mining, exactly which property was just used as a filter/sort/facet target, at the moment it happens.

### Proposed separation of responsibilities

Four distinct pieces, deliberately not one class, living in a new **`operations` partition** — a home of its own, not folded into `register.*`. Register's existing tables are materialized item/link state; this subsystem is operational metadata *about* register's own physical tables and their indexes, which is a distinct concern, not a sub-concern of current item state. The name is deliberately general (not "indexing") because the same capture → decide → act → track shape is likely reusable for other future usage-driven operational decisions, not just this one.

1. **Usage recording** — capture that property P was used as filter/sort/facet, when. Pure data collection. Not a raw per-event log (unbounded growth — a single `CollectionProjectionSpec` execution can touch several properties at once across its filter, sort, and facets). Instead, a time-bucketed counter table — one row per `(property_id, item_type_id, usage_date)`, columns for `filter_count`/`sort_count`/`facet_count`, upsert-incremented, pruned after a retention window. Bucketing by day is what makes both "fast attack" (today's bucket) and future recurring-pattern awareness (comparing bucket history) possible without unbounded storage.
2. **Index strategy** — given a property's recorded usage history (and any explicit admin override), decide whether it currently *wants* an index. Pure policy, no DDL, no DB connection needed to test. Proposed as a literal strategy-pattern seam specifically because this is the piece most likely to need tuning (thresholds, recency weighting, whether facet usage counts more than filter usage) independent of the DDL mechanics. Backed by a desired-state table: one row per property that's crossed the creation threshold, holding `desired_state`, `last_evaluated_at`, and `flagged_for_removal_at` (see removal policy below — deliberately not an immediate drop).
3. **Reconciler** ("terraform apply") — given the strategy's verdict (desired state) and what's actually in `pg_indexes` (actual state) for a type's table, diff and execute `CREATE INDEX CONCURRENTLY`/`DROP INDEX`. Pure mechanics. Uses `CONCURRENTLY` specifically because the whole point of fast-attack creation is firing on a table that's live and likely hot right now — a plain `CREATE INDEX`'s exclusive lock would defeat that.
4. **Build tracking** — `CREATE INDEX CONCURRENTLY` can fail partway through and leave an `INVALID` index behind that Postgres does not clean up on its own. A durable record of each build attempt (`property_id`, `item_type_id`, `index_name`, `started_at`, `status` — `PENDING`/`BUILDING`/`SUCCEEDED`/`FAILED_INVALID` — `completed_at`, `error_message`) is what lets the reconciler survive an app restart mid-build and know, on its next pass, to check `pg_indexes` for a leftover `INVALID` entry and clean it up before retrying, rather than silently accumulating dead index entries.

An admin override (pin always-index / never-index) fits as an input the strategy considers, or as a composed override-aware strategy wrapping the usage-based one — not a branch hardcoded into the reconciler.

### Established principles

- **"Fast attack, slow release"** (the governing asymmetry, named directly after the audio-compressor dynamic it resembles): creation and removal are not symmetric thresholds. Creation should trigger on a low bar — a property crossing even a small usage count within a short window — specifically so a sudden, legitimate burst (e.g. fiscal-quarter-end reporting against properties almost never queried the rest of the year) gets its index built within the first query or two of the burst, not after it's already mostly over. Removal should require a long, conservative hold. A naive *symmetric* policy (e.g. "unused in the last 60 days → drop") would see a quarterly-burst property as cold for 10 of 12 weeks and remove it right before the next burst — the worst possible timing, since the very next query is the burst. Note this doesn't make creation instantaneous in effect: `CREATE INDEX CONCURRENTLY` on a large table can take real wall-clock minutes, so the honest remaining cost at burst-onset is "however many queries land during the build," not zero — bounded and known, rather than unbounded. That cost is easily justified by what it buys (a one-time build amortized against potentially thousands of reads over the following burst).
- **Removal is advisory, never automatic.** The ground-truth signal for "is this index worth keeping" is Postgres's own `pg_stat_user_indexes.idx_scan` counter — not the app-level usage-recording signal from responsibility #1 above, which only proves someone *asked a question naming the property*, not that the planner ever actually chose the index in response (a property can be requested constantly while the planner still prefers a seq scan for independent reasons — table too small, poor selectivity, etc.). But `idx_scan` is still a cumulative counter evaluated over *some* window, which reintroduces the same seasonal blind spot described above no matter how accurate the underlying signal is — accuracy of what's measured doesn't fix the risk of the measurement window being shorter than a real usage cycle. The resolution: the strategy flags an index (`flagged_for_removal_at`) when `idx_scan` has stayed at zero for a long window, but the reconciler never executes the `DROP INDEX` itself — that's surfaced for a human to act on. Automating only the cheap-to-be-wrong-about half (creation) and keeping the expensive-to-be-wrong-about half (removal) human-gated is the whole point of the attack/release asymmetry.
- **Reconciliation can run asynchronously, decoupled from the write path, with zero correctness risk.** Because the blanket `GIN(properties)` always guarantees correct results regardless of whether an expression index exists yet, a missing/stale expression index is purely a performance gap, never a correctness one. `CREATE INDEX`/`DROP INDEX` are real DDL against potentially large tables and don't need to block the mutation transaction.
- **Usage recording (responsibility #1) must itself be asynchronous and failure-tolerant.** It sits in the read/projection path, so it can never add latency there or fail the request: the upsert against the usage-counter table has to be fire-and-forget relative to the projection response, and a failed upsert is logged, not retried against the live request, not escalated into a user-visible error — losing one usage data point is a non-event; slowing or breaking a read to guarantee it is not an acceptable trade. (Exact transport — a background executor, a queue, something else — is still open; see below.)
- **Index shape should be derived mechanically from `(PropertyType, PropertyCardinality)`, not chosen by the strategy.** `SINGLE`-cardinality `STRING/INT/LONG/DATE/DATETIME` get a btree expression index with an appropriate cast; `BOOLEAN` (low value even if used) and `OBJECT`/`BINARY` types, plus any `LIST`/`SET` cardinality property, rely on the existing blanket GIN rather than getting a dedicated expression index.
- Indexes the reconciler manages need **deterministic, predictable names** (e.g. `idx_<table>_<propertyId>`) rather than Postgres's auto-generated ones, so the diff against `pg_indexes` can match by name instead of parsing index definitions.

## Still open (not yet decided)

- **Resolved by discussion, not yet by number:** creation should use a low/fast threshold and removal a long/conservative one ("fast attack, slow release" — see above), but the exact numbers (how many uses within how short a window triggers creation; how long `idx_scan` must stay at zero before flagging for removal review) aren't chosen yet. Does facet usage weigh differently than filter/sort usage (faceting is inherently a heavier, repeated-query pattern) also remains open.
- Exact transport for usage recording's async, failure-tolerant write (a background executor, a queue, `LISTEN`/`NOTIFY`, something else) — the requirements are pinned (never blocks or fails the read path; a dropped update is logged and forgotten), the mechanism is not.
- The `SchemaChangeEvent` surface needs to widen before any of this can trigger at all — today it only fires on whole item-type/link-type create/delete. Trait-implemented-on-type, property-added-to-an-already-implemented-trait, and (once inheritance ships) supertype-changed/abstract-toggled don't publish any event today.
- Blast radius resolution: a change to a widely-implemented trait or a high-in-the-hierarchy supertype needs reconciliation across every currently-affected type's table, not just the one directly edited — the same "resolve the dependent type set" operation the cross-type query engine needs, likely shared machinery rather than a separate resolver.

## Why this over the alternatives, restated

Letting admins declare `queryable` per property is workable but forces a decision most schema authors aren't equipped to make well (the enum/string example demonstrated the "obvious" answer is often wrong), and cuts against wanting the system to "just work." Indexing everything or nothing are both cheap to implement and both wrong once real subtype hierarchies push property counts high. Usage-driven indexing is the one option where the deciding signal (real query behavior) is something ntrloc already has for free, precisely because search queries are structured rather than raw SQL.
