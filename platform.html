Architecture

A graph underneath, built to keep running

ntrloc's data model, how its schema evolves without migration drama, and the mechanism that lets you change schema, data, or UI — without ever going down or exposing a half-finished state.

The data model

Items, links, and traits

A graph model that's fast to read and precise to reason about.

Items live in per-type tables

Rather than one unified table for every kind of item, each item type gets its own table, sharing a common item_registry identity anchor that every link references. Read performance is the priority ntrloc optimizes for first, and per-type storage serves it directly — no filtering a single giant table by discriminator column.

Properties are stored as JSONB, keyed by immutable property IDs rather than human-readable labels — so renaming a label is a metadata change, not a data migration.

Traits keep schema DRY

A trait is a named, reusable group of property definitions. Item and link types declare which traits they implement; a type's full property set is the union of its traits plus any type-local properties.

Adding a trait to a type is non-destructive — existing items simply return null for the new properties until populated. Removing one is handled by read tolerance: orphaned values are silently ignored on read, while writes reject deprecated properties immediately.

Links are undirected, with per-participant visibility

A link has two participant slots — A and B — with no implied direction and no owner. Each slot optionally carries a label describing what that participant calls the link. A Photographer might see a "created" link to a Photo, while the Photo sees the same link as "creator" — and an unrelated item type linked with no label simply doesn't see the relationship at all. Multiple link types can share a label from a given participant's perspective, so renaming a label regroups everything that shares it, all at once.

Traversal up to roughly five hops runs efficiently via recursive queries — covering the practical depth of real ntrloc queries without requiring a dedicated graph-traversal engine underneath.

Binary data, deduplicated by content

Binary properties don't store bytes or URLs in JSONB. On upload, ntrloc streams the binary while computing MD5 and SHA-256 digests; if the combination of hash and length already exists in the binary store, the upload is discarded and the existing record is referenced instead. Identical content — a re-uploaded image, a duplicate asset — is stored exactly once, however many items reference it. ntrloc is always the pass-through for downloads, so callers never see a raw storage path, and every download is permission-checked and audited.

Schema evolution

Most schema changes aren't events

Versioning is a punctuation mark, not continuous overhead.

Because traits are reusable and non-destructive, most of what teams think of as "schema migrations" — adding a property, renaming a label, giving a type a new trait — are just metadata edits in ntrloc. There's no data to rewrite and no version to bump.

No version bump needed

Adding properties, renaming labels, adding or removing traits from a type — all routine, none of it requires a schema version change.

Version bump when it matters

Only explicit data migrations — property consolidation, trait extraction — advance the schema version, with items tagged by the version they were written under.

DDL is never manual

Table, index, and view creation are handled automatically as types and properties are registered — including expression indexes per queryable property, plus a GIN catch-all.

Uptime

Nothing goes live until you flip the switch — and nothing needs a restart

The same principle applies at every level: item writes, bulk data transformations, schema changes, and security policy changes are all staged, then committed as one atomic switch. A changeset is how you scope a change too large to verify by eye in real time.

1

Define

An admin defines the schema changes, security changes, and data transformations that make up the changeset. ntrloc calculates scope and impact up front and presents a pre-commit report before anything is built.

2

Build

The cluster builds a staged overlay in parallel. Every declared transformation begins running as a continuous process against the live write stream, not a one-time batch job — and sanity checks run throughout.

3

Stage

The staged overlay is queryable like any other view. Admins and testers browse it, diff before/after per item, review marker changes, and simulate permissions — while new live writes keep propagating into the overlay automatically. This phase can last indefinitely.

4

Commit — or discard

A single atomic switch makes the staged schema, policies, and data live, and retires the old state. Because the overlay was already current, the commit is a true switch flip, not a re-migration. Discarding costs nothing — live data is never touched until commit.

5

Clean up

The old staged overlay is physically removed in the background, and deprecated property values are stripped if desired — asynchronously, off the critical path.

The overlay itself is sparse — only items actually affected by the changeset's transformations exist in it. Unaffected items are read straight from live data, so storage cost scales with the size of the change, not the size of the dataset. And by design, ntrloc supports at most two versions at once — live and staged — trading away concurrent multi-changeset workflows for a model with no rebasing and no conflict resolution to design around.

Hot by default, not just at commit time

Staging covers schema, security, and data — but ntrloc treats UI and logic changes the same way. Hosted UI content is served straight from whatever's currently at its resource location, no compile step involved at request time. Server-rendered templates resolve without caching when their source lives outside the classpath, so an edit takes effect on the next request. Nothing in ntrloc requires a restart to ship a change — the changeset commit and the hot-reloaded template are the same underlying idea applied at different layers.
